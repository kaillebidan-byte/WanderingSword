# 校正パイプライン 現行フローとコスト特性(最適化相談用・自己完結)

> 外部に「これ以上トークンを減らせるか」を相談するための説明書。この1枚で文脈なしに読めるよう書いてある。
> 作成 2026-06-16(本セッションまでの最適化を反映)。

## 1. 何のシステムか
中国製RPG「Wandering Sword」の**日本語化MOD**。ゲームのテキストは UE4 の locres に入っている。
機械翻訳(MT)済みの日本語を、**キャラ単位で人手(LLM)が校正**している(フェーズ2)。
- 校正の主目的 = **キャラの「声」を平坦化させない**(MTは口調・人称・呼称を無難な標準語に均す)。誤訳修正は前提条件。
- 実行者 = **Claude Sonnet を手動で1回ずつ走らせる**(cron無し)。コスト(トークン)に敏感。優先度: accuracy > source_intent > consistency > efficiency > style。
- 環境 = Windowsネイティブ / Python3.12(標準ライブラリのみ) / UEパッカ `repak.exe`。

## 2. データ構造(ディスク上・静的)
- `_work/jp/.../Localization/<対象>/zh-Hans/<対象>.locres` … **現在の日本語訳(MT＋校正済)**。最終成果物。`ns\x1fkey → 文字列`。
  ※MODは「簡体字(zh-Hans)スロットを日本語で上書き」する方式。対象=Quests任务表/CG表/Npc/系统 等。
- `_phase4_proofread/by_character.json` … `{order:[キャラ…], lines:{キャラ:[[target,ns,key],…]}}`。**話者ごとの行リスト**(処理順つき)。
- `_phase4_proofread/char_progress.json` … `{ci, pos}` 現在キャラindex・行位置。**進捗の唯一の正本**(会話を引き継がずここから再開できる)。
- `_phase4_proofread/source_zh.json` … `target\x1fns\x1fkey → 原文中国語(zh)`。**原文の参照辞書**。
- `10_人物/<キャラ>.md` … キャラのペルソナ(声の核・一人称・呼称・校正変換規則・任意で `## 機械置換` 表)。
- `00_ルール/*.md` … 世界観口調指針(MT誤訳の癖一覧)・関係性呼称マップ 等の恒久ルール。

行の形式: `ID - 話者名 $@$本文`(例 `19713 - 童安 $@$本文…`)。**`$@$`より前(ID・話者名)とタグ `<Y>…</>`/`\r\n`/`#nl` は不変。本文だけ直す。**

## 3. 1回の校正フロー(現行・コマンドとI/O)
LLMセッション1回 = 1バッチ(150〜200行)。**毎回まっさらな新規セッションで下記を実行**(前会話・サマリーを引き継がない=入力肥大回避。続きは char_progress が保持)。

0. 環境: `export WS_TMP="$PWD/_ws_tmp"; export PYTHONIOENCODING=utf-8`(後者必須=無いとcp932でcrash/文字化け)。
1. `python _tools/status.py` → 現在キャラ確認。
2. **読むもの最小限**: 今回キャラの `10_人物/<キャラ>.md` ＋ `00_ルール/世界観口調指針.md` ＋ `00_ルール/関係性・呼称マップ.md` のみ。他(語調カタログ・RUNBOOK全文等)は読まない。
3. **関門**: ペルソナが `status:確定` でなければ校正せず停止(未確定の声起こしは上位モデル=Opus直轄)。
4. **機械置換(任意・コスト削減)**: ペルソナに `## 機械置換`(曖昧さゼロの1:1 JA→JA置換表=半端漢字/固定呼称等)があれば
   `python _tools/mechanical_pass.py`(WS_CHAR指定)で**LLMが読む前に**スクリプト適用。代名詞/コピュラ等の危険置換は内蔵ガードが自動拒否。
   → これで全行の約半数が無料で片付く(実測: あるキャラで369行中176行)。
5. **バッチ取得**: `python _tools/pending_char.py 200` → `$WS_TMP/pf_char_batch.tsv` を**ファイルとして読む**。
   - 形式(コスト削減のTSV): 1行目 `#META⇥{character,pos,total,completes_character}`、2行目 `#COLS`、以降 **`target⇥ns⇥key⇥zh⇥ja`** の1行1レコード。
   - stdoutには要約1行だけ(全文の二重読み込みを避ける)。
6. **校正(LLMの中核)**: 各行 `zh`(原文)と `ja`(現訳MT)を見比べ、ペルソナの声に引き戻す(register・一人称・呼称・笑い等)＋誤訳修正。
7. **修正の書き出し**: `$WS_TMP/pf_inbox.json` に**ファイル直書き**(CJKをパイプ/heredocで渡さない)。
   形式 `{"reviewed":N,"fixes":[{"target","ns","key","new_body"}]}`。
   **`new_body` は本文($@$より後ろ)だけ**(ID・話者名の接頭辞は apply_char が現訳から自動再付与。タグ・改行は本文内なので保持)。`reviewed`=見た件数(進捗前進量)。
8. **反映**: `python _tools/apply_char.py $WS_TMP/pf_inbox.json` → locres書き戻し → `_work` pak 再パック(repak) → char_progress前進 → ログ → **inbox自動削除**(次回Writeの「未読ファイル不可」制約回避)。
9. **完走時のみ監査**: completes_character=true の回だけ `python _tools/pending_char.py --audit`(WS_CHAR)→ `$WS_TMP/char_audit.txt`(ja本文のみ=grep軽量)。
   NG語を**1パスで全部grep→1回で全修正**(`reviewed:0`で進捗動かさず)。apply→audit→apply のループ禁止(=コスト主因だった)。
10. **デプロイ**: `python _tools/deploy_to_game.py`(pak再パック→ゲームの Paks へコピー→日本語自己検証)。pak操作はサブプロセス＝LLMトークン消費なし。
11. 報告: 件数/修正数/キャラ・pos/声の定性1行。

## 4. ツールのI/Oまとめ
| ツール | 入力 | 出力 | LLMトークン影響 |
|---|---|---|---|
| status.py | 進捗ファイル | 現在地(数行) | 極小 |
| mechanical_pass.py | ペルソナの`## 機械置換`＋locres | locres書換＋pak再パック | **ゼロ(LLM不介在)** |
| pending_char.py N | by_character/source_zh/locres | `pf_char_batch.tsv`(target⇥ns⇥key⇥zh⇥ja) | **大(原文zh＋現訳ja×N行)** |
| (LLM校正) | TSV＋ペルソナ＋ルール | `pf_inbox.json`(new_body) | 入力=バッチ＋資料、出力=修正本文 |
| apply_char.py | pf_inbox.json | locres書換＋pak＋進捗 | 極小(サブプロセス) |
| pending_char.py --audit | by_character/locres | `char_audit.txt`(ja本文のみ) | 中(キャラ全ja) |
| deploy_to_game.py | _work pak | ゲームへコピー＋検証 | 極小 |

## 5. これまでに入れた最適化(効果順)
1. **毎回新規セッション＋必読最小化**: 前会話サマリー(約3千語)を引き継がない／RUNBOOK全文・語調カタログ等を読まない。
2. **機械置換の先行適用**: 決定的な置換(半端漢字・固定呼称)をスクリプトで先に当て、LLMは判断系だけ。約半数の行の修正が消える。
3. **バッチTSV化＋stdout全文ダンプ廃止**: フィールド名・JSON整形を排し、stdoutへの二重出力をやめた。
4. **fixesは本文のみ(new_body)**: 接頭辞(`ID - 話者名 $@$`)を書かせず apply 側で再付与。出力減＋ID写し間違い消滅。
5. **監査1パス化＋ja-only auditファイル**: audit→fixのループを禁止、grep対象を ja本文のみに。
6. **1依頼=1バッチ／フレッシュ session を重ねる**: 1セッションで数珠つなぎに完走すると文脈が肥大して割高。小さい新規 session を重ねる方が安い。

## 6. 現在のコスト実測と「残る主役」
- 旧: 70行で約20k。 現行: **200行で約15k**(1行あたり約4倍効率)。完走の続き(別session 131行)は約3k。
- **残コストの主役 = バッチ本文(各行の zh＋ja)**。ドキュメント読みを絞った今、ここが支配的。
  - zh(原文・中国語)は本文の約4〜5割を占める。校正の「声直し」には zh は不要(ja＋ペルソナで足りる)。zh が要るのは「誤訳検出/意味確認」だけ。

## 7. 検討中／未解決の最適化論点(相談したいのはここ)
- **(A) zhのオンデマンド化**: バッチを ja-only にし、zh は `source_zh.json` から必要行だけ引く(怪しい行・意味が動く編集のみ)。
  入力〜4-5割減の見込み。ただし zh を引かない行は**誤訳を見落とす**リスク(accuracy最優先と相反)。緩和案=完走監査時に全zh突合。
- **(B) idxベースfixes**: 修正を `{i, new_body}` にし、apply側が i→(target,ns,key) をバッチから解決。出力の target/ns/key 文字列を消せる。
- **(C) その他**: LLMがバッチ全行を必ず文脈に載せる前提自体を崩せるか?(例: 機械置換で確定した行は校正対象から外して提示しない、等)
- 制約: 制御タグ(`$@$`/`<Y></>`/`\r\n`/`#nl`)は不変。CJKは `python -`/heredoc/パイプ不可(化ける)=ファイル経由必須。優先度 accuracy>source_intent>consistency>efficiency>style。
