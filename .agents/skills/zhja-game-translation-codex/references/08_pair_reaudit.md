# 08 人物ペア再監査 ── 証拠、修正束、適用・ビルド

初回翻訳やキャラ単位校正を一巡した後、人物・関係性・既訳を一次資料から再検証するための標準手順。

ペルソナと関係性マップは監査対象であり、判定の正本ではない。単語一致や既存規則に訳文を合わせる作業ではなく、**この人物が、この相手へ、この時点・場面で何をどう言うか**を復元する。

## 1. 使用条件

次のいずれかに当てはまる場合に使う。

- キャラ単位の一巡は終わったが、品質が粗い。
- ペルソナの根拠が既訳や完成例へ循環している。
- 関係性マップが静的で、入門・和解・離反・正体判明などの変化を持たない。
- 同じ相手への一人称、二人称、敬体、呼称が場面ごとに揺れている。
- 行単位では自然でも、連続場面として読むと意味、感情、言いさしが壊れている。
- 原文の機能語や関係語が、日本語の固定語へ表面転写されている。

## 2. 判定資料の優先順位

1. 原文、現訳、同一会話ブロックの前後行
2. 話者、同席者、明示された宛先
3. 時系列、分岐、関係成立前後、公私、感情状態
4. 同一人物・同一関係の別場面
5. 設定・用語の正本
6. ペルソナ、関係性マップ、過去ログ

下位資料が上位資料と矛盾する場合、訳文を下位資料へ合わせない。ペルソナやマップを改訂する。

## 3. 標準成果物

人物ペアごとに次を残す。

- **証拠インベントリ**: 原文、現訳、話者、前後行、複合キー、重複座標
- **人物ペア監査台帳**: 関係段階、場面、呼称、register、根拠、反例、確度
- **修正束JSON**: 実変更だけを収録したkey→新値
- **意図的保持記録**: 候補に上がったが、現訳を保持した行と理由
- **適用記録**: キー数、対象locres、pak、検証、未実施のゲーム確認
- **監査状態**: evidence / persona / relation / translation / build / game を分離

雛形は `templates/pair_audit_template.md`。

## 4. 監査の順序

### 4.1 関係クラスタを選ぶ

主人公単独、キャラ単独ではなく、物語上の機能が近い人物群から始める。

例:

- 師門中核
- 近親・義兄弟
- 敵対から共闘へ変わる人物
- 多モード人物
- 門派横断の役職・呼称

### 4.2 人物ペアを一つ選ぶ

一度に複数関係を裁定しない。関係の変化が他者を含む場合でも、主対象の二者を明示する。

### 4.3 一次資料を抽出する

- 二者が同席する会話ブロック
- 相手を明示して言及する行
- 呼称、二人称、師弟・親族・役職語を含む行
- 前後数行
- 分岐や重複座標

同内容の複製は統合してよいが、全座標を記録する。直前話者を自動的に宛先と見なさない。

### 4.4 関係段階へ分ける

最低でも次を確認する。

- 関係成立前 / 後
- 私的 / 公的
- 平時 / 緊張 / 病床 / 戦闘 / 儀礼
- 敵対 / 和解 / 共闘 / 離反
- 正体・秘密の判明前 / 後

静的な「AはBを○○と呼ぶ」だけで終わらせない。

### 4.5 場面単位で読む

行ごとに完結させず、一つの場面を連続して読む。

特に注意するもの:

- 複数行に分割された一文
- 咳、息切れ、沈黙、言いさし
- 呼びかけだけの短句
- 告白、継承、別れ、病床
- 選択肢前後

既に適切な短句や効果音は、周囲を直すためだけに変更しない。

## 5. 各行の裁定

候補を次の四つへ分ける。

1. **fix**: 原文・場面・人物関係から修正が必要
2. **keep**: 現訳が妥当。意図的保持
3. **source-doc-fix**: 訳文ではなくペルソナやマップが誤っている
4. **unresolved**: 宛先、時系列、分岐などが不足して判断不能

修正理由は次の軸で書く。

- meaning: 情報の追加・脱落、因果、主客、否定、固有語
- voice: 一人称、語尾、古風度、感情、短句、比喩
- relation: 呼称、二人称、敬度、公私、関係段階
- implementation: タグ、改行、話者接頭辞、表示制約

## 6. 高確度修正束の条件

修正束は10〜40キー程度を目安にし、**同じ場面または同じ崩れ方**でまとめる。件数より境界の明確さを優先する。

収録条件:

- 複合キーが実在する。
- 原文、現訳、前後文、話者、場面を確認済み。
- 新旧値に実差分がある。
- 変更理由を meaning / voice / relation のいずれかで説明できる。
- 話者接頭辞、タグ、改行、プレースホルダを変えない。
- 単語の一括置換ではない。
- 既に正しい行を含めない。

除外条件:

- 宛先不明の二人称
- 時系列不明の呼称
- 設定正本と原文が衝突し、裁定できないもの
- ゲーム表示を見なければ決められない改行・UI問題
- 好みだけの言い換え

## 7. 実装関門

### 7.1 適用前

- 修正JSON間の同一キー競合
- 対象locresとkeyの存在
- 未適用 / 適用済みの区別
- `$@$` 前の話者接頭辞
- 制御タグ、改行、プレースホルダの並び

### 7.2 適用

複数修正束をまとめて渡し、対象locresを各1回だけ書き、pakを1回だけ生成する。

```text
python _tools/apply_fixes_json.py _phase4_proofread/fixes_*.json
python _tools/apply_fixes_json.py _phase4_proofread/fixes_*.json --apply
```

同一キーに異なる新値がある場合は、書き込み前に停止する。未適用が0件ならrepakしない。

### 7.3 適用後

- 全修正束のプレビューが `計0件`
- 修正値とlocresの一致
- register lint
- 関係性一次資料の再抽出
- 単体テスト
- pak実体とLFS管理

ゲームフォルダへの配置とゲーム内確認は別段階。

## 8. GitHub運用

プロジェクトに恒久workflowがある場合、人物ペアごとの一時workflowを作らない。

推奨:

1. 監査ブランチへ新しい `fixes_*.json` を追加
2. PRを作成
3. 読み取りCIで修正束・抽出・lintを検証
4. 書き込みCIが同一リポジトリPRの未適用分だけを反映
5. locresとLFS pakがPRブランチへ戻る
6. botによる再実行では書き込みジョブを停止
7. 最終HEADの恒久CI成功後にマージ

workflowへ人物名、日付、バッチ番号をハードコードしない。修正束はglobまたは明示manifestで検出する。

## 9. ペルソナへの還元

監査で確定した規則だけをペルソナへ戻す。

各規則に次を付ける。

- 主張
- 根拠キー
- 相手と場面
- 時系列条件
- 反例
- 確度 high / medium / low

完成例も根拠キーを持たせる。既訳を根拠なしに完成例へ流用しない。

## 10. 実運用から得た注意

- 中国語 `为师` は日本語の固定自称「師」ではない。主語省略、自称、師としての機能を場面で選ぶ。
- 一律の「あなた」「お前」「です・ます」は関係段階を消す。
- `拜帖` など関係・儀礼を担う語は、一般語へ早合点しない。
- 病床や最後の願いは、文法的に整った長文へ直しすぎない。短句、息切れ、言いさしを保つ。
- 咳だけの行、沈黙、既に正しい短句は、周囲の修正束へ機械的に含めない。
- 一つの人物ペアを複数束に分けてもよい。各束の場面境界と累計を記録する。
