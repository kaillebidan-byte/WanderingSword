# 02 立ち上げ・再監査RUNBOOK ── Phase 0〜7

ゼロから翻訳プロジェクトを起こし、初回一巡後の品質再監査とビルド検証まで進める手順。各Phaseは前のPhaseの成果物を前提にする。

**ペルソナ未確定のキャラ本文に着手しない**ことは初回作業の安全弁。ただしペルソナは最終正本ではなく、一巡後に一次資料で再検証する。

## 役割分担の運用

|役割|担当|してよいこと|してはいけないこと|
|---|---|---|---|
|監督|計画・ペルソナ作成と改訂・典故同定・関係裁定・抜き取り検査・統合・ビルド判定|解釈を含む全判断、修正適用、pak生成|根拠なしの一括統一、ユーザー専用ゲームフォルダの操作|
|翻訳・監査ワーカー|register固定バッチの翻訳、人物ペアの候補整理、提案、完了報告|確定作業仮説の範囲で訳す、反例を報告する|ペルソナを反証不能な正本として適用、未確定キャラへの初回着手、ゲームへのデプロイ|
|機械処理|計数・整形・抽出・lint・キー検証・locres書き戻し・再パック|曖昧さゼロの処理|解釈を要する変換|

エスカレーション: ワーカーは迷った行に `conf:low` と理由を付ける。カノン外・ペルソナ外は `# REVIEW`、一次資料とペルソナが衝突する場合は `# PERSONA_CONFLICT`。無言で平均化しない。

## Phase 0: テキスト抽出とコーパス整備

1. ゲームからテキストを抽出する。UnityならTextAsset等、UEならlocres等を対象にする。
2. 原文言語と正本を確認する。簡体字・繁体字が併存する場合は制作国・実データ・更新状況で正本を決める。
3. `key → 原文` の対応表を作る。JSONL等の機械処理可能な形式を推奨。
4. 制御タグ、改行、プレースホルダ、話者接頭辞を棚卸しする。
5. keyの構造から会話、地の文、戦闘、UI等の層を推定する。
6. 書き戻し経路を確立し、1件だけゲーム内表示まで疎通確認する。バックアップを取る。

成果物: コーパス、タグ保全リスト、抽出・書き戻しスクリプト、初回疎通記録。

## Phase 1: 文体基盤と話者インベントリ

1. `03_style_guide.md` を読み、世界観口調指針を作る。
2. 会話行を話者別に集計する。
3. 大物・中物・端役へ区分する。端役へ過剰な個性を足さない。
4. テキスト層ごとの文体を宣言する。

成果物: 世界観口調指針、話者インベントリ、進捗表。

## Phase 2: ペルソナ設計

主要キャラから順に `04_persona.md` の手順で初回作業用ペルソナを作る。

- 素材は原文、自称・二人称・呼称統計、代表場面。
- `templates/persona_template.md` を使い、根拠キーを残す。
- `status: 確定` は初回作業へ着手可能という意味。最終品質保証ではない。
- モード別の手本訳は根拠キーと場面を添える。既訳を根拠なしに完成例へ流用しない。
- 反例と未確定項目を消さずに残す。

成果物: `10_人物/<キャラ>.md` 群。

## Phase 3: 用語・呼称基盤

1. 武功名、門派、地名、アイテム、UI語彙を原文から抽出し、確定訳・仮訳のstatus付き用語ノートへ入れる。
2. 呼称マップを話者×相手で作る。師兄・師弟、親族、役職の向きを相互確認する。
3. 関係成立前後、公私、敵対・和解などの時系列列を持たせる。
4. 参考対訳は語彙慣例と言い回しの型だけに使い、固有名詞を流用しない。

成果物: 用語ノート、初回関係性・呼称マップ、参考TM。

## Phase 4: 本文翻訳・初回校正

翻訳ワーカーによるバッチループ。`templates/worker_prompt_template.md` をプロジェクトに合わせて使う。

- キャラ単位×register固定バッチ。1バッチ100〜200行を目安にする。
- cursorをファイルへ永続化する。
- 冒頭で読む資料をペルソナ、世界観口調指針、該当関係・呼称、style guideへ絞る。
- 出力はkey付きJSON。適用処理と判断処理を分離する。
- 10バッチごとに監督が抜き取り検査する。
- 傾向不良が出たら個別修正だけでなく、ペルソナ、呼称マップ、プロンプトを疑う。
- 分岐場面は選択肢を横並びで確認する。

キャラ単位の完走は `initial_pass`。最終品質保証とは記録しない。

## Phase 5: 証拠中心の品質再監査

`08_pair_reaudit.md` を正本として進める。

1. 関係クラスタを選ぶ。
2. 人物ペアを一つ選ぶ。
3. 原文・現訳・前後文・話者・時系列・重複座標を抽出する。
4. 関係段階と場面へ分ける。
5. ペルソナと関係性マップの主張を根拠・反例つきで検証する。
6. 既訳を meaning / voice / relation の三面で再読する。
7. `fix / keep / source-doc-fix / unresolved` へ分ける。
8. 同一場面または同一崩れ方の高確度修正だけを、10〜40キー程度の修正束へまとめる。

行単位の単語置換ではなく、連続会話・関係変化・公私・感情状態で裁定する。既に正しい短句、咳、沈黙、効果音は機械的に修正束へ含めない。

成果物: 証拠インベントリ、人物ペア監査台帳、修正束JSON、意図的保持、資料改訂、監査状態。

## Phase 6: 修正適用とビルド検証

解釈が終わった修正束だけを決定的処理へ渡す。

1. 複数JSON間の同一キー競合を検査する。
2. key、話者接頭辞、タグ、改行、プレースホルダを検査する。
3. 全修正束をまとめてlocresへ反映する。
4. 対象locresは各1回だけ書き、pakを1回だけ生成する。
5. 適用後プレビューが0件になることを確認する。
6. lint、関係抽出、単体テスト、pak実体、LFS管理を確認する。
7. 適用記録と監査状態を更新する。

標準コマンド:

```text
python _tools/validate_fixes_json.py --allow-applied _phase4_proofread/fixes_*.json
python _tools/apply_fixes_json.py _phase4_proofread/fixes_*.json
python _tools/apply_fixes_json.py _phase4_proofread/fixes_*.json --apply
```

未適用が0件ならrepakを省略する。同一キーの修正値が競合する場合は、書き込み前に停止する。

GitHub Actionsを使う場合、人物・日付・バッチ番号をハードコードした一時workflowを作らず、修正束を動的検出する恒久workflowを使う。

この段階は `build_verified`。ゲーム内確認ではない。

## Phase 7: ゲーム内検証

- ゲームフォルダへの配置はプロジェクトの権限境界に従う。
- フォント、文字化け、改行、タグ、UIはみ出し、場面適合を確認する。
- 重要な感情場面、分岐、呼称変化、長文UIを優先する。
- 表示制約が判明した修正は、意味・声を保ったまま別修正束へ戻す。

ゲーム内で確認したものだけを `game_verified` とする。

## 記録の規律

- `initial_pass / evidence_inventory / persona_reviewed / relation_reviewed / translation_reaudited / build_verified / game_verified` を分離する。
- 詳細ログはアーカイブへ、開いているTODOだけを短い一覧へ置く。
- AGENTS.mdは地図であり、手順を重複させない。
- 修正束の件数、対象、適用状態、pak、ゲーム確認の有無を記録する。

## 実行環境の落とし穴

- `PYTHONIOENCODING=utf-8` を設定する。
- CJKを含むコードやJSONをPowerShellのパイプ・stdin・heredocで渡さず、UTF-8ファイルへ書く。
- 中間ファイルはプロジェクト内の専用ディレクトリへ置く。
- repakのバージョンとmount pointを固定する。
- locres/pakのビルドとゲームフォルダへのデプロイを分離する。
